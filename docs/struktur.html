01Der Überblick

Vier Teile, eine Schnittstelle

In der Mitte steht eine einzige ausführbare Datei. Sie enthält die Datenbank, den Webserver, die Spielregeln und die fertige Weboberfläche. Daran hängen drei Arten von Geräten, und alle drei reden dieselbe Sprache: /api/opx.

Der Grundsatz dahinter: Eine Datei, ein Doppelklick, ein Spiel. Alles, was zusätzlich installiert werden müsste, wäre eine Stelle, an der ein Spieltag scheitern kann. Deshalb keine Datenbank daneben, kein Webserver davor, keine Laufzeitumgebung darunter.

Alle Zugriffsregeln sind gesperrt. PocketBase stellt für jede Tabelle eine allgemeine Schnittstelle bereit (/api/collections/…/records). 06Der Weg einer Meldung

Von der Hosentasche bis auf den Bildschirm der Zentrale

Eine Architektur versteht man am schnellsten, wenn man einer einzelnen Sache beim Durchlaufen zusieht. Hier: einer Standortmeldung. 

1. Telefon    Die Ortung im Hintergrund hat einen Punkt.
             Er wandert zuerst in den Puffer auf dem Gerät —
             im Funkloch bleibt er dort liegen.
             android/…/location/LocationService.kt

2. Funk       Der Rumpf wird verschlüsselt: AES-256-GCM, Beiwerk ist
             "POST /api/opx/position nummer". Schlüssel und Nummer
             stehen in den Kopfzeilen.
             android/…/data/Funk.kt · ios/…/Data/Funk.swift

3. Tunnel     Falls einer läuft: Cloudflare sieht HTTPS, entschlüsselt es
             — und findet darunter die zweite Verschlüsselung.

4. Server     Eine Zwischenschicht entschlüsselt den Rumpf, bevor
             irgendein Endpunkt ihn sieht. Der übrige Server weiß von
             der Verschlüsselung nichts.
             pkg/api/secure.go

5. Prüfung    Gehört das Team zu diesem Spiel? Ist die Meldung plausibel
             — Tempo, Genauigkeit, Fake-GPS-Kennzeichen des Geräts?
             pkg/api/position.go

6. Regeln     War die Frist fällig? Dann Verwarnung, Abzug oder Sperre.
             Läuft eine Mission? Dann zählt der Abstand zum Ziel.
             pkg/game/

7. Ablage     Position, Ping und gegebenenfalls eine Buchung im Kontobuch.

8. Lagestrom  Der Hub weckt alle offenen Ströme. Die Zentrale sieht den
             Punkt binnen einer Sekunde, die Fahndung einen Kreis von
             200 Metern — falls sie ihn sich erarbeitet hat.
             pkg/hub/ · pkg/api/stream.go

9. Zurück     Die Antwort wird mit demselben Schlüssel versiegelt und
             sagt dem Gerät, wann die nächste Meldung fällig ist.
Gewertet wird der Erfassungszeitpunkt, nicht der Eingang. Sonst wäre jedes Funkloch eine Strafe. Deshalb trägt jede Meldung ihren eigenen Zeitstempel, und der Puffer darf nachreichen, ohne dass jemand dafür bestraft wird.

07Die zwei Verschlüsselungen

Warum eine nicht reicht

Der Tunnel macht den Server von unterwegs erreichbar, ohne dass jemand einen Anschluss öffnen oder ein Zertifikat besorgen muss. Er endet aber nicht auf dem Spielserver, sondern beim Betreiber des Tunnels — dort liegt der Verkehr im Klartext. Bei diesem Spiel wäre das der Standortverlauf von zwanzig Leuten über sechs Stunden.

Deshalb verschlüsselt jedes Gerät ein zweites Mal, unabhängig vom Tunnel: ECDH auf P-256, daraus per HKDF-SHA256 ein Sitzungsschlüssel, damit AES-256-GCM. Dasselbe Verfahren steht viermal im Projekt, und diese drei Einzelheiten müssen überall zeichengenau übereinstimmen:

  • Das Salz von HKDF ist eigenerSchlüssel|Serverschlüssel, beide base64url ohne Auffüllzeichen.
  • Das Beiwerk ist METHODE /pfad?abfrage nummer — mit Abfrageteil.
  • Übertragen werden Chiffrat und Siegel hintereinander, der Zufallswert steht in der Kopfzeile.
WoDatei
Serverpkg/crypt/ · pkg/api/secure.go
Browserweb/src/lib/funk.svelte.js
Androidandroid/…/data/Funk.kt
iOSios/OperationX/Data/Funk.swift
Das Kennzeichen ist die einzige Stelle, an der sich ein untergeschobener Server verrät: sechs Gruppen aus vier Zeichen, oben im Gerät und auf der gedruckten Teamkarte. Sind sie gleich, sitzt niemand dazwischen. Die Apps merken sich das Kennzeichen jedes Servers und warnen, wenn dieselbe Adresse plötzlich ein anderes nennt.

Was das nicht leistet: Der Spielserver sieht weiterhin alles — er ist das Spiel. Und wer mitliest, sieht weiterhin, wann wie viel an welche Adresse geht. Wer den Rechner hat, hat die Datenbank.

08Die drei Oberflächen

Dieselbe Schnittstelle, drei Werkzeuge

Browser (Svelte 5)

Die vollständige Oberfläche: Einrichtung, Regelpult, Druck, Zentrale, Zeitleiste — und auch das Feld, für alle, die keine App installieren wollen. Wird beim Bauen in die Binary eingebettet. Zustand über Runen ($state, $derived), Lage über einen Ereignisstrom.

Android (Kotlin, Compose)

Für das Feld gebaut. Ortung im Hintergrund mit gesperrtem Bildschirm, Puffer fürs Funkloch, QR-Scanner (ZXing), Karte mit MapLibre. Hält eine offene Verbindung zum Server und erfährt jede Änderung in unter einer Sekunde.

iOS (Swift, SwiftUI) — Entwurf

Dieselben Bildschirme, dieselben Texte, MapKit statt MapLibre, kein eigener QR-Scanner (die Kamera-App kann das). Fragt alle zehn Sekunden nach, statt zuzuhören. Übersetzt ist bisher nur, was ohne Apple-SDK geht — die Verschlüsselung allerdings vollständig: gegen den gemeinsamen Prüfvektor und gegen einen echten Server (ios/Funkprobe/pruefen.sh).

Was überall gleich sein muss: die Texte der Einweisung, die drei Parteifarben (Zielperson rot, Fahndung blau, Zentrale gold) und das Beiwerk der Verschlüsselung. Alles andere darf sich unterscheiden, wo die Plattform es nahelegt.

09Wo dieses Programm aufhört

Ein Server, ein Spiel — und was darüber liegt

Dieses Programm führt genau ein Spiel. Das ist keine Einschränkung, die man später wegräumt, sondern die Voreinstellung: ein Nachmittag, ein Laptop, eine Gruppe. Im Quelltext dieses Verzeichnisses kommt der Gedanke „mehrere Spiele“ nirgends vor.

Wer mehrere Spiele gleichzeitig führen will — eine Klassenfahrt mit drei Gruppen, oder ein Server, den mehrere Gruppen nacheinander benutzen — braucht eine Ebene darüber: Konten, Trennung, Fristen, eine Übersicht. Die liegt in einem eigenen Projekt, operation-x-server. Es bindet dieses hier als Bibliothek ein und hängt sich an wenigen Stellen ein:

HakenWofür
api.ZusatzroutenWeitere Endpunkte, nach den eigenen registriert
api.StatusZusatzWeitere Felder in der Antwort auf /status
api.EinrichtungOffenOb die Ersteinrichtung noch aussteht
api.ServerSacheWer Sicherung und Tunnel schalten darf
api.SpielDesServersWelches Spiel eine Anfrage ohne Anmeldung meint
api.RufzeichenWie ein Anmeldename gebildet wird
schema.NacharbeitEigene Sammlungen und zusätzliche Felder
aufsatz (Web)Drei Steckplätze in der Oberfläche
Warum getrennt und nicht als Schalter. Ein Schalter hätte bedeutet, dass jeder, der einen Geburtstag ausrichtet, im Quelltext und in der Anleitung über Veranstalterkonten stolpert — und dass jede Frage zweimal beantwortet werden muss: „und wie ist das, wenn mehrere Spiele laufen?“ Getrennt beantwortet jedes Verzeichnis nur seine eigene Hälfte.

10Bauen und Prüfen

Die Reihenfolge und was sie garantiert

# Nach dem Klonen genügt ein Befehl: holt die Werkzeuge, baut, prüft
./bauen.sh

# Von Hand — Oberfläche zuerst, sie wird in die Binary eingebettet
cd web && npm install && npm run build && cd ..
go build -o operationx ./cmd/operationx

# Alles auf einmal, für Windows, macOS und Linux
./scripts/build-release.sh

# Prüfen
go test ./pkg/...              Regeln, Sichtbarkeit, Spieltrennung, Löschen
cd web && npm test                 der Kern der Verschlüsselung
cd android && ./bauen.sh           prüft, baut, spielt auf ein Gerät
cd ios/Funkprobe && ./pruefen.sh   iOS-Verschlüsselung gegen echten Server

Was die Tests festhalten:

  • Das Regelwerk kann nicht unbemerkt altern. Jede Zahl in regelwerk.html trägt den Schlüssel ihres Regelwerts; ein Test vergleicht 98 Zahlen mit den Voreinstellungen im Code.
  • Die Sichtbarkeit stimmt. Was ein Fahndungsteam von der Zielperson sieht, ist ein Unschärfekreis — geprüft, nicht behauptet.
  • Die Verschlüsselung passt zwischen den Sprachen. Alle vier rechnen denselben Prüfvektor nach (testdaten/lagefunk.json): dieselbe Ableitung, dasselbe Beiwerk samt Abfrageteil, dieselben Bytes. Der Prüfstand in ios/Funkprobe tut das für Swift und redet zusätzlich mit einem laufenden Server.
  • Die Bewegungsspur verschwindet wirklich. Ein Test legt ein Spiel mit Positionen, Beweisfoto und Sperre an, lässt die Frist ablaufen und sieht nach, was übrig ist.
